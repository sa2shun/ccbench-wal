\section{Proposal: Ayame}
\label{sec:design}

Ayame is a logging method that integrates durable write-ahead logging
into SSN while avoiding the three problems of P-WAL identified in
Section~\ref{sec:background}.  It combines three techniques.
First, it reuses the commit timestamp that SSN already assigns as the
logical log sequence number, eliminating the separate WAL-side global
counter (addresses \textbf{P1}).  Second, it splits commit processing
into worker, flusher, and committer roles so that worker threads do not
block on \texttt{fdatasync} or durable-ack waiting, subject only to a
bounded backpressure limit (addresses \textbf{P2}).
Third, it acknowledges a transaction using a \emph{dependency-closed
durable frontier} instead of a global durable prefix, so that a
transaction waits only for the log records it actually depends on
(addresses \textbf{P3}).

We use the following notation.  A frontier $F$ is a vector of per-shard
log positions.  $F \fjoin F'$ denotes the element-wise maximum,
$F \le F'$ holds iff $F[i] \le F'[i]$ for every shard $i$, and $\bot$
denotes the empty frontier whose positions are all zero.  $D$ denotes
the durable vector, where $D[i]$ is the largest log position of shard
$i$ that is known to be durable; each $D[i]$ advances monotonically.

\subsection{Commit Timestamp as Logical LSN}
\label{sec:cstamp}

In SSN, a committing transaction $T$ is assigned a commit timestamp
$T.c$ (its \emph{cstamp}) that fixes its position in the serialization
order.  We assume that
SSN assigns a unique commit timestamp to each committed update
transaction, so these timestamps form a total order that recovery uses
as the replay order.  A separate
WAL-side global LSN, as used by P-WAL, would redundantly re-encode the
same logical order and add a second global-counter access to every
commit.  Ayame instead reuses $T.c$ directly as the logical LSN that
orders recovery replay.  No WAL-side global sequence number is
allocated; in our evaluation the per-transaction WAL-side global-counter
access drops to zero.

Removing the global \emph{logical} LSN does not remove physical log
addressing.  Each WAL shard keeps a local position (a per-shard
sequence number and byte offset) that locates a record within its log
file.  What Ayame eliminates is the duplicated global ordering counter,
not the per-shard physical position.

\subsection{Worker, Flusher, and Committer Separation}
\label{sec:pipeline}

Ayame divides commit processing into three roles.  A \emph{worker}
executes the transaction, validates it with SSN, assigns the commit
timestamp, appends the log record to its own WAL shard, publishes
durability metadata, and registers a durable-acknowledgment request.
The worker then returns to its next transaction; it does not call
\texttt{fdatasync} and does not wait for a durable acknowledgment.  A
\emph{flusher} owns one WAL shard, batches the queued records, writes
them, calls \texttt{fdatasync}, and advances the shard's durable
position.  A \emph{committer} returns durable acknowledgments to clients
once the durable condition of a registered transaction is met.  Workers
therefore do not block on storage synchronization or durable-ack
waiting, and keep executing transactions at full concurrency even though
every update commit must still be made durable; the cost of making the
log durable is paid by the flusher and committer.  The one exception is
a bounded backpressure limit: to cap memory use and acknowledgment
latency, a worker stalls only if the number of registered but
not-yet-acknowledged durable commits reaches a configured maximum.
Accordingly, we report throughput as the number of durable
acknowledgments returned to clients, not the number of logical commits.

Algorithm~\ref{alg:ayame-commit} shows the worker-side commit protocol.
The commit timestamp $T.c$ assigned for SSN validation doubles as the
logical LSN (line~\ref{ln:cstamp}).  After validation, the worker
reserves its log position on its shard (line~\ref{ln:reserve}) and forms
the closed frontier $F$ by extending its dependency frontier $T.\dep$
with that position (line~\ref{ln:closed}).  It then builds the log
record, whose commit record carries $F$ (line~\ref{ln:build}), and
enqueues it without flushing or waiting (line~\ref{ln:enqueue}).  Ayame
installs $F$ as the write frontier of the versions $T$ created
(line~\ref{ln:pub-w}) and publishes those versions
(line~\ref{ln:publish}); a version becomes visible only after its write
frontier is installed, so any later reader or overwriter observes the
writer's complete frontier.  It also merges $F$ into the read frontiers
of the versions $T$ read (line~\ref{ln:pub-r}).  Finally, the worker
registers $F$ for durable acknowledgment (line~\ref{ln:register}) before
returning a logical commit.

\begin{algorithm}[t]
\caption{\bfseries Worker-Side Commit Protocol (Ayame)}
\label{alg:ayame-commit}
\begin{algorithmic}[1]
\Function{Commit}{$T$}
    \State $T.c \gets$ commit timestamp (cstamp) assigned by SSN
           \label{ln:cstamp}
           \Comment{logical LSN}
    \If{\Call{SsnValidate}{$T$} fails}
        \State abort $T$; \Return
    \EndIf
    \If{$T$'s write set is empty} \Comment{read-only}
        \State \Call{Ack}{$T$}
               \Comment{read-only has no recoverable effect}
        \State \Return logical read-only commit
    \EndIf
    \State $s \gets$ WAL shard assigned to this worker
    \State $T.\lseq \gets$ \Call{ReserveSeq}{$\mathit{wal}[s]$}
           \label{ln:reserve}
           \Comment{reserve this transaction's log position}
    \State $F \gets T.\dep$; \quad $F[s] \gets \max(F[s], T.\lseq)$
           \label{ln:closed}
           \Comment{closed frontier}
    \State $r \gets$ \Call{BuildRecord}{$T.c, F, T.\mathit{write\_set}$}
           \label{ln:build}
           \Comment{commit record carries $F$}
    \State \Call{Enqueue}{$\mathit{wal}[s], r$}
           \label{ln:enqueue}
           \Comment{append only; no flush, no wait}
    \ForAll{versions $v$ created by $T$}
        \State $v.\wfr \gets F$ \label{ln:pub-w}
    \EndFor
    \State \Call{PublishVersions}{$T.\mathit{write\_set}$}
           \label{ln:publish}
           \Comment{visible only after $\wfr$ is installed}
    \ForAll{versions $v$ read by $T$}
        \State $v.\rfr \gets v.\rfr \fjoin F$ \label{ln:pub-r}
               \Comment{monotone merge}
    \EndFor
    \State \Call{Register}{$F, T$}
           \label{ln:register}
           \Comment{durable ack deferred to the committer}
    \State \Return logical commit
\EndFunction
\end{algorithmic}
\end{algorithm}

The flusher does not require an algorithm of its own.  Each flusher owns
one WAL shard, repeatedly collects the records queued by workers, writes
them as a single batch, calls \texttt{fdatasync} once for the batch, and
then advances the shard's durable position by invoking
\textsc{OnDurableAdvance} (Algorithm~\ref{alg:ayame-ack}).  Batching many
records per \texttt{fdatasync} is what raises the number of commits made
durable per synchronization and reduces flush pressure relative to
P-WAL's per-transaction synchronization.

\subsection{Dependency-Closed Durable Acknowledgment}
\label{sec:depack}

The remaining question is when a logically committed transaction may be
acknowledged as durable.  Ayame answers this with a frontier attached to
each version.  A version carries a \emph{write frontier} $\wfr$, the
closed frontier of the transaction that created it.  A writer publishes
$\wfr$ before its version becomes visible, so any transaction that later
reads or overwrites the version observes the complete write frontier of
its producer.  During execution, a transaction joins these write
frontiers into its dependency frontier $T.\dep$, as shown in
Algorithm~\ref{alg:ayame-dep}: reading a version makes $T$ depend on the
writer of that version (line~\ref{ln:dep-read}), and overwriting a
version makes $T$ depend on the writer of the version it supersedes
(line~\ref{ln:dep-write}).  A version also carries a \emph{read frontier}
$\rfr$, into which readers monotonically merge their closed frontiers;
\textsc{OverwriteVersion} additionally joins $\rfr$ so that an overwriter
conservatively tracks the readers of the version it supersedes.  As
discussed below, this last term is an anti-dependency over-approximation
that the safety argument does not rely on.  Transactions known to be
read-only skip WAL generation and durable-acknowledgment registration.
When the read-only fast path applies, they also avoid dependency-frontier
collection; otherwise, only lightweight read-path frontier bookkeeping
may remain.

\begin{algorithm}[t]
\caption{\bfseries Dependency Collection (Ayame)}
\label{alg:ayame-dep}
\begin{algorithmic}[1]
\Function{Begin}{$T$}
    \State $T.\dep \gets \bot$
\EndFunction
\Statex
\Function{ReadVersion}{$T, v$}
    \State add $v$ to $T$'s read set
    \If{$T$ is known read-only}
        \State \Return \Comment{SI read-only fast path}
    \EndIf
    \State $T.\dep \gets T.\dep \fjoin v.\wfr$ \label{ln:dep-read}
           \Comment{the writer of $v$}
\EndFunction
\Statex
\Function{OverwriteVersion}{$T, v$}
    \State add the new version to $T$'s write set
    \State $T.\dep \gets T.\dep \fjoin v.\wfr \fjoin v.\rfr$
           \label{ln:dep-write}
           \Comment{the writer of $v$ and its readers}
\EndFunction
\end{algorithmic}
\end{algorithm}

At commit, the closed frontier $F$ (line~\ref{ln:closed} of
Algorithm~\ref{alg:ayame-commit}) extends $T.\dep$ with $T$'s own log
position.  By induction over the dependency order, $F$ therefore
contains the log positions of the transitive closure of the read-from
and version-order (write-write) dependencies of $T$, all of which are
recorded through write frontiers.  Publishing $F$ as the write frontier
of the versions written by $T$ lets future readers and overwriters
inherit $T$'s closed frontier through Algorithm~\ref{alg:ayame-dep}.
Merging $F$ into the read frontier of the versions read by $T$
conservatively delays future overwriters of those versions, but this
read-frontier term is not required for the safety proof.

Algorithm~\ref{alg:ayame-ack} shows the committer side.
\textsc{Register} parks $T$ on each shard whose durable position has not
yet reached the requirement of $F$ (line~\ref{ln:park}); if no shard is
behind, $T$ is acknowledged immediately (line~\ref{ln:dur-check}).
\textsc{OnDurableAdvance}, invoked by a flusher after \texttt{fdatasync},
advances the durable position of one shard and wakes the parked
transactions whose requirement on that shard is now satisfied, releasing
the acknowledgment once a transaction's last outstanding shard becomes
durable (line~\ref{ln:ack-ready}).  \textsc{Register} and
\textsc{OnDurableAdvance} execute under a single lock so that a durable
advance cannot slip between the durability test and the parking step.

\begin{algorithm}[t]
\caption{\bfseries Durable Acknowledgment (Ayame)}
\label{alg:ayame-ack}
\begin{algorithmic}[1]
\Statex \textbf{State:} durable vector $D$; per-shard waitlists $W[i]$
        ordered by required position
\Function{Register}{$F, T$}
        \Comment{atomic w.r.t.\ \textsc{OnDurableAdvance}}
    \State $T.\mathit{remaining} \gets 0$
    \ForAll{shards $i$ such that $F[i] > D[i]$}
        \State $T.\mathit{remaining} \gets T.\mathit{remaining} + 1$
        \State insert $(F[i], T)$ into $W[i]$ \label{ln:park}
    \EndFor
    \If{$T.\mathit{remaining} = 0$}
        \State \Call{Ack}{$T$}
               \label{ln:dur-check}
               \Comment{own record and all dependencies durable}
    \EndIf
\EndFunction
\Statex
\Function{OnDurableAdvance}{$i, d$}
        \Comment{called by flusher $i$ after \texttt{fdatasync}}
    \State $D[i] \gets d$
    \While{$W[i]$ is not empty and \Call{MinKey}{$W[i]$} $\le d$}
        \State $(\mathit{need}, T) \gets$ \Call{PopMin}{$W[i]$}
        \State $T.\mathit{remaining} \gets T.\mathit{remaining} - 1$
        \If{$T.\mathit{remaining} = 0$}
            \State \Call{Ack}{$T$} \label{ln:ack-ready}
        \EndIf
    \EndWhile
\EndFunction
\end{algorithmic}
\end{algorithm}

The acknowledgment rule is exactly $F \le D$: a transaction is
acknowledged once its own record and every record it transitively
depends on are durable.  We now make the safety of this rule precise.
For a committed update transaction $U$, let $s_U$ and $U.\lseq$ be the
shard and position of its log record, so its published closed frontier
$F_U$ satisfies $F_U[s_U] \ge U.\lseq$.  Let $\mathrm{cl}(T)$ be the set
of update transactions reachable from $T$ through read-from dependencies
($T$ reads a version written by $U$) and version-order dependencies ($T$
overwrites a version written by $U$), including $T$ itself.  Both kinds
of dependency are recorded by joining the relevant version's write
frontier, which its writer publishes before the version becomes visible.

\begin{lemma}[Dependency-closed durability]
\label{lem:closure}
If \textsc{Ack}$(T)$ is invoked, then for every update transaction
$U \in \mathrm{cl}(T)$ the WAL record of $U$ is durable.
\end{lemma}

\begin{proof}
Dependency collection (Algorithm~\ref{alg:ayame-dep}) joins the write
frontier of each version $T$ reads or overwrites into $T.\dep$, and the
commit protocol sets $F = T.\dep$ with $F[s_T] \ge T.\lseq$
(line~\ref{ln:closed}).  A writer publishes its write frontier before
its version becomes visible, so $T$ observes the complete frontier
$F_U$ of every $U$ it directly depends on; since each $F_U$ is itself
closed, induction over the dependency order gives $F \ge F_U$, hence
$F[s_U] \ge F_U[s_U] \ge U.\lseq$, for every $U \in \mathrm{cl}(T)$.
\textsc{Ack}$(T)$ is invoked only when $F \le D$
(Algorithm~\ref{alg:ayame-ack}), so $D[s_U] \ge U.\lseq$.  Since $D[i]$
is a durable prefix of shard $i$, the record of $U$ is durable.
\end{proof}

Each commit record stores the transaction's commit timestamp $T.c$ and
its closed dependency frontier $F$, alongside the redo records that carry
the write set.  During recovery, Ayame reconstructs the durable vector
$D$ by parsing each shard's records in order and advancing $D[i]$ until
the first record that does not parse as a complete, well-formed entry,
which indicates a torn final write; records beyond that point are
ignored.  A distinguished commit marker identifies each transaction's
commit record.  Ayame then collects the committed transactions whose
commit records lie within $D$, keeps only those whose stored frontier is
covered by the durable vector (that is, $F \le D$), and replays this
dependency-closed set in increasing cstamp order.  Because the replayed
set is closed under $F \le D$, a recovered transaction never appears
without the transactions it depends on, even if its own commit record
happened to be durable while a dependency's was not.

\begin{theorem}[Recoverable acknowledgment]
\label{thm:recover}
Suppose a crash occurs and recovery replays exactly the durable WAL
records in logical-LSN order.  If $T$ was acknowledged before the crash,
recovery never yields a state that contains the effects of $T$ but omits
the effects of some $U \in \mathrm{cl}(T)$.
\end{theorem}

\begin{proof}
By Lemma~\ref{lem:closure}, every $U \in \mathrm{cl}(T)$ has a durable
record and is therefore replayed.  Each dependency edge $U \to T$ is a
serialization edge of SSN, so $U$'s commit timestamp precedes $T$'s;
because logical LSNs equal commit timestamps, replay in logical-LSN
order installs every such $U$ before $T$.  Hence whenever $T$'s effects
are installed, the effects of all $U \in \mathrm{cl}(T)$ are already
present.
\end{proof}

The lemma and theorem rest only on write frontiers, which are published
before a version is visible and are therefore observed completely by
every reader and overwriter.  The read-frontier term that
\textsc{OverwriteVersion} joins (the $\rfr$ of an overwritten version)
makes acknowledgment additionally wait for the readers of that version,
an anti-dependency.  This term is a conservative over-approximation: it
can only delay an acknowledgment, never release one early, and the
safety argument above does not use it.  Because readers publish $\rfr$
concurrently with overwriters, it is a best-effort addition rather than
a guaranteed bound, which is why we keep the proof over write frontiers
alone.

The rule is also less conservative than a global durable prefix: a
transaction waits only on the shards that appear in its frontier, so an
unrelated slow shard never delays it.
