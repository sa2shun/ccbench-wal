\section{Evaluation}
\label{sec:evaluation}

\subsection{Implementation}
\label{sec:impl}

We implement Single WAL, P-WAL, and Ayame on
CCBench~\cite{tanabe2020ccbench}, a concurrency-control benchmarking
framework with minimal functionality for protocol analysis, using
Masstree as the index and \texttt{mimalloc} as the allocator.  The code
is written in C++20 and compiled with GCC at the \texttt{-O3}
optimization level.  Our implementation is publicly
available.\footnote{The source code is available at
\url{https://github.com/sa2shun/ccbench-wal/tree/cstamp-pwal-framework}.}

A key methodological point is that Single WAL, P-WAL, and Ayame are
implemented in the \emph{same} binary and selected at run time by
environment flags (\texttt{CCBENCH\_WAL\_MODE} and
\texttt{CCBENCH\_WAL\_DURABLE\_MODE}).  The CCBench SI+SSN protocol
implementation, the index, the workload generator, and the pre-commit
path are therefore identical across the three systems; only the WAL
durability path differs.
Single WAL appends to one shared log under a global latch and
synchronizes it per commit.  P-WAL gives each worker a private WAL shard
and synchronizes it per commit, acknowledging through a global durable
prefix.  Ayame uses the worker/flusher/committer pipeline of
Section~\ref{sec:design} with dependency-closed acknowledgment.  Ayame keeps
one WAL shard per flusher, so the number of shards equals the flusher count
(nine at 48 workers) and is smaller than the worker count; each worker is
mapped to a shard and several workers share one, which lets a flusher batch
many workers' records into a single \texttt{fdatasync} (in contrast to P-WAL,
which gives every worker a private shard).  The dependency frontier is thus a
vector over these shards, and the per-shard sequence reservation is shared by
co-located workers.  Each WAL
redo record carries the key, value, storage identifier, and operation
type of a write; the terminating commit record additionally stores the
transaction's commit timestamp and its closed dependency frontier, which
recovery uses to admit only the dependency-closed set of durable
transactions.  Read-only WAL skipping is
enabled for all three systems; once a transaction is known to be
read-only it produces no WAL record.  For read-only transactions Ayame
also skips durable-acknowledgment registration, but depending on the
read path it may still execute lightweight frontier bookkeeping; YCSB-C
quantifies this residual overhead.

Following the worker/flusher/committer separation of
Section~\ref{sec:design}, Ayame offloads durability to background
threads: it uses 1, 3, 5, 7, 9, 12, 14, 17, and 19 flusher threads for 1,
12, 24, 36, 48, 60, 72, 84, and 96 worker threads, respectively, and one
committer thread in all configurations.  The x-axis of our worker-scaling
experiments is the number of transaction worker threads; at 48 workers
Ayame therefore runs 58 active threads (48 workers, 9 flushers, and one
committer).  At 96 workers Ayame runs 116 active threads (96 workers, 19
flushers, and one committer), which exceeds the 96 logical cores of the
machine; we revisit this oversubscription when discussing the high-thread
end of the sweep.

\subsection{Experimental Configuration}
\label{sec:config}

\subsubsection{Environment}
\label{sec:env}

Experiments were conducted on a server with two sockets of Intel(R)
Xeon(R) Gold 5418N CPUs.  Each socket had 24 physical cores with two
hardware threads per core, for 48 physical and 96 logical cores in
total, organized as two NUMA nodes.  Each core had a 48\,KiB private L1d
cache and a 2\,MiB private L2 cache, and each socket shared a 45\,MiB L3
cache.  The DRAM capacity was 256\,GB.  The machine ran Ubuntu 22.04.5
LTS (Linux kernel 5.15), and WAL files were placed on a locally attached
SSD formatted with ext4.  Worker threads were pinned to distinct logical
cores with \texttt{sched\_setaffinity}.

\subsubsection{Benchmark and Workloads}
\label{sec:workloads}

All experiments used the Yahoo! Cloud Serving Benchmark
(YCSB)~\cite{cooper2010ycsb}.  We evaluated three representative workloads:
YCSB-A (50\% read, 50\% update), YCSB-B (95\% read, 5\% update), and
YCSB-C (read-only).  These workloads exercise the WAL along a spectrum
from update-heavy to read-only and are widely used to evaluate
concurrency-control protocols.  Each transaction issued a fixed number
of ten operations over a database of 100{,}000 records with 4-byte
values, and keys were drawn from a uniform distribution.

\subsubsection{Metric}
\label{sec:metric}

The primary metric is \emph{durable-acknowledgment throughput}: the
number of transactions acknowledged as durable to the client, divided by
the measurement time.  All systems are measured at the same stop
barrier, and acknowledgments drained during shutdown are excluded.  For
the worker-wait systems (Single WAL and P-WAL) a logical commit and a
durable acknowledgment coincide, so the metric has the same meaning
across the three systems.  We additionally report the p99 durable
acknowledgment latency and the number of pending (not-yet-acknowledged)
durable commits.  Unless otherwise stated, each reported value is the
mean of the corresponding per-run metric over five runs; reported p99
latencies are means of the per-run p99 values.

\subsection{Results}
\label{sec:results}

This section evaluates Ayame as a complete durable-acknowledgment pipeline.
The results show that Ayame substantially improves end-to-end throughput on
update workloads by decoupling workers from batched durable flushing, while
keeping tail latency and pending durable commits small.  The remaining
throughput decline at high thread counts is caused by contention in the
underlying SSN concurrency-control layer rather than by the WAL pipeline.

\subsubsection{End-to-End Throughput Improves on Update Workloads}

We evaluate Ayame using the worker-thread sweep of Table~\ref{tab:params},
which adds a single-thread baseline and then spans 12 to 96 worker threads in
steps of 12 (up to the full two-socket machine).
Figure~\ref{fig:ycsbabc-worker-throughput} plots the durable-acknowledgment
throughput across the sweep, and Table~\ref{tab:ycsbabc-48worker-summary} lists
the 48-worker numbers.  At 48 worker threads on YCSB-A, Single WAL achieves 9K
durable acknowledgments per second and P-WAL achieves 50K, whereas Ayame
achieves 253K; on YCSB-B, Single WAL achieves 26K and P-WAL 165K, whereas Ayame
achieves 467K.  These are
5.1$\times$ and 2.8$\times$ improvements over P-WAL on YCSB-A and YCSB-B, and
the Ayame-over-P-WAL ratio stays large across the sweep, ranging from
6.5$\times$ at 12 workers to 4.1$\times$ at 96.

This gain comes from Ayame's durability pipeline as a whole, mainly from
decoupling workers from batched durable flushing (\textbf{A2}); reusing the
commit timestamp as the logical LSN (\textbf{A1}) is a design simplification
that removes duplicated logical ordering rather than a direct throughput
optimization.  This end-to-end comparison should therefore not be read as
isolating the effect of dependency-closed acknowledgment (\textbf{A3}), whose
contribution we isolate in Section~\ref{sec:why-dep}.

We also evaluate YCSB-C, where all transactions are read-only and WAL records
are skipped.  Durability work largely disappears: with the same binary and a
read-only empty-frontier fast path, the three systems land within about 8\% of
one another at 48 worker threads (872K for Single WAL, 808K for P-WAL, and 812K
for Ayame in ); Ayame is marginally
below Single WAL because it may still execute lightweight read-path frontier
bookkeeping.  We therefore use YCSB-C as a sanity check for read-only
bookkeeping overhead rather than as evidence of WAL persistence performance.

\subsubsection{Tail Latency and Pending Durable Commits Remain Small}

Ayame keeps pending durable commits small
: at 48 worker threads it holds 318
pending commits with a 2\,ms p99 acknowledgment latency on YCSB-A, and 83 with
a 0.5\,ms p99 on YCSB-B.  Figure~\ref{fig:ycsbabc-worker-latency} shows that this
p99 stays low across the whole sweep.  The asynchronous pipeline therefore keeps
up with the offered durable-logging load at every thread count; it does not buy
throughput by letting an unbounded backlog accumulate.  The zero pending count
of Single WAL and P-WAL does not mean that they avoid waiting; their workers
wait synchronously on the commit path, so the wait shows up as lower throughput
rather than as an asynchronous pending queue.

\subsubsection{The Scalability Ceiling Comes from SSN Contention}

The high-thread throughput decline is a known scalability limit of the
underlying SSN concurrency control, not a limit of Ayame's WAL pipeline: SSN
certifies serializability through centralized metadata---a single global
commit-timestamp counter (which Ayame reuses as the logical LSN, \textbf{A1})
and a central transaction-mapping table---and this metadata does not scale to
many cores~\cite{tanabe2020ccbench}.  Concretely, Ayame's YCSB-A throughput
peaks near 24--36 workers (294--296K) and then declines toward 96 workers
(209K); YCSB-B follows the same shape, and P-WAL declines in parallel.
Figure~\ref{fig:scalability-breakdown} traces the cause to per-transaction cost
rather than to aborts.  The cycles spent per committed transaction rise steeply
with thread count---about 2.8$\times$ on YCSB-A (136K at 12 workers to 375K at
96) and 2.2$\times$ on YCSB-B---consistent with cache-line contention on these
shared structures as they bounce between cores' caches; because the
per-transaction cost grows faster than the core count, throughput falls once the
contention outweighs the added parallelism.  Aborts, by contrast, cannot explain
the decline: the abort rate never exceeds 1.5\% on YCSB-A and 0.03\% on YCSB-B,
and YCSB-B shows the same decline with that near-zero abort rate.  Nor is the
decline thread oversubscription: P-WAL carries no background flush threads, so at
96 workers it runs 96 threads on the 96 logical cores without oversubscribing
them, yet its throughput falls in parallel with Ayame's.  Finally, the limit is
upstream of durability---the p99 acknowledgment latency stays at or below 2\,ms
across the whole sweep (Figure~\ref{fig:ycsbabc-worker-latency}) and the pending
durable commits remain small ---so the
flushers and committer are not the bottleneck; the ceiling is set by the
concurrency-control layer that Ayame inherits through cstamp reuse.

\subsection{Acknowledgment-Policy Comparison}
\label{sec:why-dep}

This section isolates the effect of dependency-closed acknowledgment
(\textbf{A3}).  Both variants use the same asynchronous worker/flusher/committer
pipeline and differ only in the acknowledgment condition: the
\emph{global-prefix} variant acknowledges a transaction only after a single
global durable prefix covers its logical commit position, whereas the
\emph{dependency-frontier} variant acknowledges it once the shard positions in
its dependency frontier are durable.  The results show that \textbf{A3} trades
some short-window throughput for bounded pending durable commits and much lower
tail latency.

\subsubsection{A3 Bounds Backlog and Tail Latency, Not Raw Throughput}

The benefit of dependency-closed acknowledgment is not that a transaction has
many dependencies; it appears when a transaction does \emph{not} depend on some
slow or lagging WAL shards, because global-prefix acknowledgment still waits for
those shards whereas the dependency frontier does not.

reports the result.
On YCSB-A the contrast is sharp: once multiple WAL shards are active, the
global-prefix variant stays pinned near the 65{,}536 backpressure limit with a
131\,ms p99 acknowledgment latency, whereas the dependency-frontier variant
remains below 500 pending durable commits---far below the global-prefix
queue---with a 1--4\,ms p99.  At 48 workers, for
instance, global-prefix holds 64{,}197 pending commits and 131\,ms while
Ayame holds 455 and 2\,ms.  Even without injecting an artificial straggler,
natural progress variation among the WAL shards is enough to keep the
global durable prefix behind, so the global-prefix queue never drains; the
dependency-frontier rule does not wait for unrelated shards and therefore
drains regardless of worker count.  On YCSB-B, whose update load is an
order of magnitude lighter, the dependency-frontier rule again holds the
pending count under about 100 and the p99 at 1\,ms across the whole sweep,
while the global-prefix rule drains at low-to-mid worker counts but
saturates beyond 48 workers as shard progress fluctuates.  (Pending counts
here are the measurement-window snapshot, as in
; these acknowledgment-policy
runs are separate from the main worker-scaling runs, so values differ
slightly due to run-to-run variation.)  This comparison also decomposes the end-to-end gain.  Moving from P-WAL's
worker-wait commit to Ayame's asynchronous worker/flusher/committer pipeline
(techniques \textbf{A1} and \textbf{A2}), while still acknowledging at the
global durable prefix, raises YCSB-A throughput at 48 workers from 50K to 444K
durable acknowledgments per second---about 8.9$\times$, and the source of
Ayame's throughput advantage over P-WAL.  Switching the acknowledgment rule of
that same pipeline from global-prefix to the dependency frontier (\textbf{A3})
is \emph{not} a throughput optimization in this short measurement window: it
lowers throughput to 251K.  The global-prefix variant can show higher
short-window acknowledgment throughput because it accumulates a large backlog
and releases many acknowledgments in bulk when the prefix advances, at the cost
of a saturated pending queue and high tail latency.  Dependency-closed
acknowledgment instead bounds the backlog and tail latency, cutting pending
durable commits from 64{,}197 to 455 and the p99 from 131\,ms to 2\,ms.  Because the two variants share the same pipeline and differ only in
the acknowledgment condition, this comparison isolates the effect of
\textbf{A3}.


\subsubsection{Avoiding Unrelated-Shard Waits Helps Even with Sparse Frontiers}

The benefit comes from not waiting for shards a transaction does not depend on,
so it should not require dense dependency frontiers.  Zipfian skew does not let
us vary frontier density: it changes which keys are hot
but not which WAL shards wrote them, so in a non-partitioned workload the
writers of the accessed versions stay spread across all shards and the
dependency frontier remains dense.  We therefore vary the frontier width
directly with an abort-free partitioned workload in which each worker owns
a key partition and a remote-access probability controls how often a
transaction touches other partitions.  With \texttt{remote}\,$=0$ every
transaction depends only on its local shard---a sparse frontier of one
shard per transaction (nz/tx\,$=1$)---and with remote accesses the
frontier quickly becomes dense (about nine shards).  The jump is abrupt
because dependency frontiers compose transitively---once a transaction touches
a remote partition it inherits that partition's own frontier---so even a 1\%
remote-access probability pulls in almost all shards.  Because this
abort-free workload commits---and therefore logs---on every transaction,
it is the most write-intensive workload in our evaluation; the flush group
of 256 commits () keeps the flush pipeline unsaturated
for \emph{both} acknowledgment policies, so the remaining difference
reflects only the acknowledgment rule rather than flush-pipeline
saturation.

reports the result.  The global-prefix rule
essentially saturates the pending-ack queue and holds a 131\,ms p99 at
every density, including the fully sparse case, because it waits for the
global durable prefix regardless of what a transaction actually depends
on.  The
dependency-frontier rule keeps the pending count to a few hundred
commits and the p99 to about 2\,ms across the whole

Crucially, even when each transaction depends on a single shard
(nz/tx\,$=1$), the dependency-frontier rule still keeps pending durable
commits and tail latency far below the global-prefix rule: about
400 versus 65{,}000 pending commits, and 2\,ms versus 131\,ms p99.  The value of dependency-closed acknowledgment
is therefore not that a transaction has many dependencies, but that it
does not wait for the shards it does not depend on, and this value
remains when frontiers are sparse.


\subsection{Hardware Counters and Overhead}
\label{sec:overhead}

 reports a perf-stat comparison of the three
systems at 48 worker threads, showing two sources of Ayame's throughput
improvement and one overhead.
First, Ayame amortizes storage synchronization: it makes 23 commits durable per
\texttt{fdatasync} on YCSB-A and 14 on YCSB-B, whereas Single WAL and P-WAL
synchronize roughly once per transaction (Tx/sync of 1.0--2.5).  Second, Ayame
spends far fewer CPU cycles per committed transaction than P-WAL (243K versus
1.15M on YCSB-A): in P-WAL a worker cannot proceed until its own commit is
durable, so worker progress is coupled to storage synchronization, whereas
Ayame's workers enqueue a log record and return to execution.  Single WAL, in
contrast, barely uses the machine (1.8 cores) because its workers serialize on
a single shared log.  Third, this decoupling is
paid for in context switches, of which Ayame performs the most, reflecting the
worker/flusher/committer hand-offs.  On read-only YCSB-C, the three systems
converge in throughput, core utilization, and cycles per transaction; Ayame
still incurs more context switches due to the background pipeline, but this does
not materially affect read-only throughput.  These perf-stat runs are separate from
the main throughput runs and carry profiling overhead, so their absolute
throughputs are lower (for instance, YCSB-C reads about 683K here versus 812K
in ; we use them only for the relative
cross-system comparison.
